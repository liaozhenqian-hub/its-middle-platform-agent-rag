# PostgreSQL 问答链路延迟优化设计

## 背景与证据

系统切换到 PostgreSQL 与 pgvector 后，健康检查和数据完整性正常，但网页问答出现长时间加载。对同一审批流问题进行脱敏复现后，客户端总耗时约 223 秒：HTTP/SSE 首事件前约 35 秒，Agent 执行约 83 秒，答案产生后到终止事件约 105 秒。

当前本地运行参数为单连接池、无溢出连接、5 秒连接回收。Telepresence 下复用连接的简单查询约 0.2 至 0.8 秒，而重新取得或建立连接约 1.3 至 4.4 秒。身份、会话范围、历史、记忆、质量记录、Worker 与检索共享同一数据库引擎。质量完成阶段还会逐条写入跨度，每条跨度分别申请写连接和读连接，放大了网络延迟。

## 目标

- 保留 PostgreSQL 与 pgvector，不回退 SQLite 或 Chroma。
- 本地 Telepresence 问答首事件不再因单连接池排队数十秒。
- 质量跨度使用一次批量事务写入，不再按条重复申请连接。
- 质量采集失败不得改变用户问答结果。
- SSE 终止事件不再等待非关键质量记录全部持久化。
- 不改变 Chat API、SSE 事件、质量表结构和管理端公开接口。

## 方案比较

### 方案 A：只调整连接池

将本地连接池改为 5 个基础连接、5 个溢出连接、10 秒等待、1800 秒回收。改动最小并能快速缓解问题，但逐条质量写入仍会放大任何数据库网络抖动。

### 方案 B：连接池、批量写入和响应解耦（采用）

在方案 A 基础上增加批量跨度写入，并让 SSE 终止事件先返回用户，再由受控后台任务完成质量记录。该方案同时处理配置根因和代码级放大效应，风险可通过仓储与 API 测试控制。

### 方案 C：独立质量消息队列与 Worker

将全部质量事件写入队列，由独立 Worker 消费。隔离最彻底，但需要新增可靠队列、重试、幂等和运维资源，不适合本次本地/dev 收敛。

## 详细设计

### 连接池

本地 `.env` 使用：

```dotenv
DATABASE_POOL_SIZE=5
DATABASE_MAX_OVERFLOW=5
DATABASE_POOL_TIMEOUT_SECONDS=10
DATABASE_POOL_RECYCLE_SECONDS=1800
```

`.env.example` 已采用相同安全默认值。本次不修改或提交数据库地址、账号、密码和其他 Secret。dev 初期可根据单 Pod 压测将基础池调整到 10，但不照搬 Java 的 40/15 配置。

### 批量质量跨度

`QualityRepository` 新增 `record_spans(values)`：

- 一次验证所有跨度；
- 在一个事务和一个连接中完成全部 INSERT；
- 使用一次批量 SELECT 返回结果；
- 保留 `record_span(value)`，内部委托批量接口，兼容现有调用方；
- PostgreSQL 继续复用同一仓储契约，不新增数据库分支判断。

`QualityCaptureService._record_completion_spans` 将一次调用批量接口。整批失败只记录异常类型，不输出问题、回答、Prompt、引用正文或凭证。

### SSE 与质量持久化解耦

Chat SSE 收到 `run.completed`、`approval.required` 或 `run.error` 时：

1. 先生成并发送现有终止事件；
2. 将质量完成操作交给应用级受控后台任务；
3. 后台任务失败只写脱敏错误类型，不回写或修改已经发送的用户回答；
4. lifespan 关闭阶段等待已有质量任务短暂收尾，超时后取消，避免服务无限等待；
5. 同一个 run ID 只调度一次完成任务。

质量开始记录仍保留在请求入口，以便生成反馈标识；连接池恢复后其耗时应明显下降。

## 错误处理与兼容性

- PostgreSQL 不可用时沿用现有降级与 readiness 状态。
- 质量批量写入失败不影响 Chat 主链路。
- 同步 JSON Chat 接口暂不异步化，避免改变其响应语义；本次优先修复网页与飞书使用的 SSE 链路。
- 质量记录最终一致，不保证终止事件到达时管理端已立即看到完整跨度。
- 不改变 pgvector 检索、Embedding、Rerank、Agent 路由和模型配置。

## 测试与验收

- 仓储测试：多条跨度只进入一次写事务，并能按输入顺序返回；空列表返回空结果；单条接口保持兼容。
- Service 测试：完成阶段只调用一次批量接口；批量失败不会抛到用户链路。
- API 测试：终止 SSE 事件先于慢速质量完成返回；后台任务最终完成；失败时用户仍收到原终止事件。
- 配置测试：连接池参数合法，`.env.example` 与上线文档一致。
- 回归：质量、Agent API、SSE、PostgreSQL 仓储与应用 lifespan 测试通过。
- 实测：重启单 Worker 后，同一审批流问题首事件明显早于当前 35 秒，终止事件不再额外等待约 105 秒；readiness 中 PostgreSQL、pgvector、质量库与 Worker 均为 available。

## 非目标

- 本次不引入 Redis、Kafka 或独立质量 Worker。
- 不调整模型、Prompt、知识切分和向量内容。
- 不修改数据库表结构或重新迁移向量。
- 不以关闭质量采集作为长期解决方案。
