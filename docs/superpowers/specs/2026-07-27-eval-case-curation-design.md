# 回归评测集整理设计

## 目标

将当前混合的 138 条评测用例拆成用途明确的集合，使“回答准确率”只由具备事实、证据和行为约束的用例衡量，同时保留必要的路由表达覆盖和多轮会话验证。

## 集合边界

- `critical-v2`：30 条核心准确率用例。必须有必需事实、禁止事实、任务类型和必要证据约束；每日回归只运行这一集合。
- `conversation-regression`：10 条多轮行为用例，验证追问、上下文切换和飞书线程隔离，不计入语义准确率。
- `routing-smoke`：24 条代表性表达，覆盖审批流、指标平台、工作流和跨领域路由，只衡量路由、工具和响应行为。
- `routing-archive`：其余 70 条公开广度题，保留在数据库但停用，避免污染周回归和后台主视图。
- `critical-reserve` 与 `real-high-risk`：缺少必需事实的 3 条候选暂时停用，补齐事实后再晋级。
- 已驳回且从未产生结果的 2 条 `safety-evidence` 用例删除；其意图由 Critical 中的证据校准用例覆盖。

## 数据安全

整理脚本在任何写操作前使用 SQLite backup API 创建带时间戳的完整备份，并导出仅含用例 ID、原集合和目标动作的 JSON 清单。脚本支持 dry-run，重复执行结果一致。已有评测运行和结果不删除；只有明确驳回且没有结果引用的用例允许物理删除。

## 选择规则

24 条路由冒烟题由 3 条跨领域守卫题、7 条审批流、7 条指标平台和 7 条工作流组成。每个领域同时保留口语和正式表达，并优先选择系统高频能力：审批人、转办、版本、指标查询与权限、工作流变量、异常、重试和循环。

缺失的 `write-delete-metric` 从项目内 60 条业务数据集恢复，然后应用 `critical_cases.py` 中的官方约束。这样官方 Critical 的代码定义、数据库数量和定时任务选择保持一致。

## 验证

整理后数据库应有 137 条记录、64 条启用记录：30 条 Critical、10 条多轮、24 条路由冒烟。官方 Critical ID 必须完整且每条都有必需事实；归档、候选和保留项全部停用；两条被驳回用例不存在。最后运行迁移单测和数据库只读审计。
